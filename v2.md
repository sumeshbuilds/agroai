# AgroAI v2 — Product, System, and UI Upgrade Plan

> **Recorded:** 4 November 2026  
> **Status:** Agreed planning baseline; this document does not mean the planned features are implemented.  
> **Purpose:** Preserve the complete v2 direction, decisions, safeguards, and implementation roadmap for future work.

## 1. Product Direction and Confirmed Decisions

**AgroAI v2: Protect your land. Care for your plants.**

AgroAI becomes one farm-protection application with two main workspaces:

1. **Land Security:** satellite field monitoring, phone-camera monitoring, and animal/person alerts.
2. **Plant Security:** crop selection, complete care guides, weather-based advice, plant-photo assessment, and safe treatment links.

The experience should be playful, gamified, and graphic-rich, inspired by the user's visual references. Real monitoring status and urgent actions must remain clear and trustworthy.

### Confirmed by the user

| Decision | Agreed direction |
|---|---|
| First audience | Farmers in Kalahandi, Odisha, India |
| Languages | Odia and English |
| First camera hardware | Phone cameras; CCTV/IP cameras later |
| Budget | Free-first pilot; paid infrastructure considered when needed for reliability and scale |
| App structure | One dashboard and two main workspaces: Land Security and Plant Security |
| Visual direction | Complete UI redesign, gamification, heavy graphics, original agricultural illustrations |

### Scope and authority

- This document records the v2 roadmap, not shipped functionality.
- Existing application code and documentation describe the implementation that must be inspected before changes.
- Preserve existing farmer, farm, crop, and detection data.
- Saving this plan does not authorize automatic implementation, deployments, database changes, purchases, or paid service subscriptions.
- Reconcile `ARCHITECTURE.md`, `DATABASE_SCHEMA.md`, and other implementation documentation as the migration progresses; do not silently treat planned capabilities as existing ones.

## 3. New UI Direction: Farm Guardian

### 3.1 Visual personality

The app should feel like an illustrated farm companion, not a generic business dashboard.

- An original AgroAI plant mascot; working name: **Mati**.
- Chunky, soft 3D illustrations of plants, cameras, fields, weather, and tools.
- A small illustrated farm scene that changes with the selected crop's growth stage.
- Rounded panels, bold headings, tactile buttons, and collectible task badges.
- Lime green for primary actions, purple for progress and discovery, and warm off-white backgrounds.
- Dark forest-green text for strong outdoor readability.

The farm scene is illustrative. It is not a satellite image, a reconstruction of the farmer's land, or a claim about actual crop health.

### 3.2 Proposed visual system

| Element | Direction |
|---|---|
| Background | Warm paper `#F7F4EB` |
| Primary accent | Lime `#B8EE45` |
| Secondary accent | Purple `#7052D8` |
| Main text | Forest `#18382B` |
| Warning | Amber, with explicit text and icon |
| Urgent alert | High-contrast red, separate from game styling |
| English typography | Friendly, readable rounded type |
| Odia typography | Noto Sans Oriya, with generous line height |
| Controls | Large, approximately 48–56 px touch targets |
| Motion | Short, purposeful transitions; reduced-motion support |

Validate contrast and font rendering during implementation. Do not depend on color alone to communicate severity.

### 3.3 Graphics without making the app slow

Use pre-rendered 3D WebP/AVIF assets rather than loading a 3D engine throughout the app.

Planned asset set:

- Mascot poses: welcome, guide, task complete, attention.
- Land Security and Plant Security illustrations.
- Crop-specific illustrations.
- Growth-stage artwork.
- Weather icons and task badges.

Maps and detection models load only when needed. The phone-camera recorder remains lightweight so decorative graphics do not compete with AI detection for battery and GPU resources.

## 5. Land Security: Functional Design

### 5.1 Satellite monitoring

Satellite monitoring should provide:

- Farm boundary over imagery.
- Acquisition date and image freshness.
- Cloud/quality information.
- Before/after comparison.
- Vegetation trends where the field is large enough for meaningful analysis.
- Possible significant land-cover changes that require inspection.

#### Important limits

- Sentinel-2 imagery has approximately 10 m resolution for relevant bands.
- Updates are periodic and cloud-dependent, not real-time.
- Small plots may contain too few usable pixels.
- Vegetation change does not automatically mean pest damage or encroachment.
- Satellite imagery cannot establish legal ownership or detect a person entering the field in real time.

#### Processing flow

```text
Saved farm boundary
        ↓
Scheduled search for new satellite scenes
        ↓
Cloud and quality checks
        ↓
Crop imagery to the field and calculate supported indicators
        ↓
Compare with suitable earlier observations
        ↓
Show dated evidence and an inspection recommendation
```

Use Copernicus data first, subject to account requirements and processing quotas. Keep the current map basemap clearly separate from dated monitoring observations.

For unusable imagery, show **"No suitable recent observation"**, not a healthy-field score.

### 5.2 Phone-camera monitoring

Build on the existing camera system:

1. Farmer pairs a spare phone using a QR code.
2. Assigns it to a field and names its position, such as "North entrance."
3. Checks the camera view.
4. Draws detection zones on the camera image.
5. Chooses monitoring hours and relevant animal categories.
6. Enables detection and tests notifications.

The field boundary and camera-image zones are different coordinate systems. A camera's GPS location is not the exact location of a detected animal.

#### Monitoring status

Show separate indicators for:

- Camera connection.
- Detection enabled/disabled.
- Last frame received.
- Notification permission/delivery setup.
- Coverage limitations.

Avoid an unconditional **"Your farm is protected"** message when the camera is disconnected.

### 5.3 Animal and person alerts

```text
On-device detection
        ↓
Repeated sightings + zone/schedule checks
        ↓
Confirmation and duplicate suppression
        ↓
Save event and evidence
        ↓
Dashboard alert + background push
        ↓
View / acknowledge / snooze / mark false alarm
```

Each alert should include:

- Person or supported animal category.
- Camera name.
- Detection time.
- Evidence image and bounding box.
- Whether it was detector-confirmed or additionally AI-checked.
- Clear actions.

Use **"Person detected in the monitored zone"**, not automatically "Criminal" or "Unauthorized intruder." Object detection does not establish identity or intent.

Evaluate supported animal classes locally. The existing model must not be presented as reliably detecting every wildlife species.

### 5.4 Pilot limitations

A browser-based phone camera needs:

- A suitable spare phone.
- Secure mounting and weather protection.
- Power and connectivity.
- The camera page kept active.

Screen-off/background operation and night detection are not dependable across all phones. A single camera cannot cover an entire farm automatically.

CCTV, night-vision hardware, and edge gateways belong to the later production phase.

## 6. Plant Security: Functional Design

### 6.1 Crop selection and complete care guides

Start with a locally validated shortlist:

- Paddy/rice.
- Cotton.
- Maize.
- Ragi/millets.
- Selected pulses.
- Common seasonal vegetables.

Confirm varieties and guidance with KVK/OUAT expertise before publication.

For each planted crop, record:

- Field.
- Crop and optional variety.
- Sowing/transplanting date, or approximate age.
- Irrigation method.
- Season and expected duration.

Every supported crop gets a full lifecycle guide:

| Stage | Coverage |
|---|---|
| Before planting | Land preparation, seed selection, planting conditions |
| Establishment | Sowing/transplanting and early care |
| Growth | Irrigation, nutrition, weeds, scouting |
| Flowering/fruiting | Stage-specific care and stress warnings |
| Pest management | Symptoms, inspection, prevention, safe treatment options |
| Harvest | Readiness, handling, and storage basics |

Guides should be versioned and reviewed. AI may explain verified guidance; it should not invent an agronomic program.

### 6.2 Weather to farmer action

Combine:

- Farm-location forecast.
- Crop.
- Growth stage.
- Irrigation context.
- Reviewed decision rules.

Instead of merely showing **"Rain expected,"** show actionable guidance, for example:

> Rain is forecast. Check drainage in low areas and review today's irrigation before watering.

This is an example of the intended presentation, not a current weather report.

Possible advice categories:

- Rain and drainage.
- Heat and water stress.
- Wind-related treatment precautions.
- Suitable field-work windows.
- Weather conditions associated with pest/disease risk.

Label forecasts and model-derived soil moisture as estimates, not measurements from a field sensor.

### 6.3 Photo-based pest and disease assessment

The current weather-risk feature is not pest detection. Keep these separate.

New assessment flow:

1. Select the affected crop.
2. Take/upload clear photos.
3. Add symptoms and affected area.
4. Run image-quality checks.
5. Assess likely pest, disease, or non-pest stress.
6. Present evidence, uncertainty, and next inspection steps.
7. Offer reviewed management options where appropriate.

Result states:

- Likely issue, with supporting observations.
- Several possible causes.
- Insufficient image quality.
- Unable to assess; seek expert help.

Do not present an AI-generated confidence percentage as a validated probability. Uncertain results should not trigger chemical recommendations.

### 6.4 Safe treatment and Amazon.in links

Treatment recommendations must come from a reviewed crop–pest–formulation catalog, not free-form AI guesses.

Order the advice as:

1. Confirm the problem.
2. Scouting and preventive measures.
3. Non-chemical/IPM options.
4. Approved chemical options, where appropriate.
5. Purchase links.

Before showing a pesticide option, validate:

- Crop and target-pest approval.
- Active ingredient, concentration, and formulation.
- Current restrictions.
- Label instructions and relevant safety intervals.
- Protective equipment and weather precautions.

Never invent a dose, product approval, or Amazon product listing.

Amazon links should use reviewed matching products. If only search is available, label it **"Search Amazon.in"**, not "Verified product."

Availability, seller quality, and delivery to Kalahandi must not be assumed. Affiliate links, if introduced later, must be disclosed.

## 7. Gamification That Encourages Useful Work

Gamify care routines and learning, not danger or pesticide consumption.

### 7.1 Rewardable activities

- Completing farm setup.
- Testing a camera.
- Reviewing the care guide.
- Scouting plants.
- Recording a crop observation.
- Completing an appropriate scheduled task.

### 7.2 Progress system

- Optional XP and levels.
- Crop-stage milestones.
- Weekly missions.
- Badges such as "Field Ready," "Care Routine," and "Plant Observer."
- Gentle completion animations.

### 7.3 Guardrails

- No XP for buying or spraying pesticides.
- No rewards for collecting more intrusion events.
- No punishment for weather-related task postponement.
- No invented plant-health score.
- Crop age/progress must not imply healthy growth.
- Urgent alerts must not be hidden behind mascot animations.

Task completion and XP should be idempotent so offline retries cannot award points repeatedly.

## 8. Technical Architecture

### 8.1 Recommended approach: a modular monolith

Keep the existing stack initially:

- Next.js App Router, TypeScript, React, Tailwind.
- Drizzle and Postgres on Neon.
- Leaflet maps.
- On-device TensorFlow detection.
- Existing weather and crop-guide foundations.

Do not introduce microservices or migrate the database simply for the redesign.

```text
Farmer dashboard / Field camera phone
                   ↓
            Next.js application
                   ↓
       Authenticated domain services
          ├── Land monitoring
          ├── Plant care and scans
          ├── Weather advice
          ├── Tasks and progress
          └── Alerts
                   ↓
       Postgres + private media storage
                   ↓
       Background worker / scheduled jobs
          ├── Satellite processing
          ├── Notification retries
          ├── Camera-offline checks
          └── Advisory refresh
```

### 8.2 Notifications

For the pilot:

- Adaptive polling for an open dashboard.
- Service worker and Web Push for background alerts.
- Local siren only after the farmer enables it.
- Notification outbox with retries and duplicate suppression.

A local browser notification alone does not provide reliable closed-tab delivery. Push behavior must be tested on the actual supported devices, and network/OS restrictions remain relevant.

### 8.3 Media

The current schema stores the latest camera frame as text. Evolve this toward:

- Private media storage.
- Lightweight frame/evidence metadata in Postgres.
- Short-lived authorized access.
- Reduced preview upload rates when nobody is watching.
- Event evidence rather than continuous video archives.

### 8.4 Data additions

Extend existing tables and introduce only necessary domains:

- Camera devices and detection zones.
- Satellite observations.
- Plant scans and advisories.
- Care tasks and completions.
- Progress ledger.
- Multi-device push subscriptions.
- Notification outbox.
- Media metadata.

Crop guides and treatment catalogs can start as versioned bilingual content rather than requiring an admin CMS immediately.

Use appropriate dates/time zones, ownership constraints, indexes, and database-enforced tenant isolation.

## 9. Security, Localization, and Reliability

### 9.1 Security priorities

- Require a strong production authentication secret; remove production fallback behavior.
- Rate-limit PIN login, pairing, uploads, and AI scans.
- Use expiring/revocable camera credentials.
- Separate device-upload permission from farmer-management permission.
- Enforce ownership for farms, cameras, scans, alerts, and media.
- Validate uploads and protect cookie-authenticated mutations.
- Keep camera evidence private.
- Provide understandable consent, retention, and deletion controls.

Proposed pilot retention: short-lived previews, seven-day event evidence, and thirty-day event metadata, configurable after farmer/privacy review.

### 9.2 Odia and English

Translate the actual experience, not only navigation:

- Setup instructions.
- Guides and tasks.
- Alert messages.
- Assessment uncertainty.
- Treatment precautions.
- Offline and error messages.

Use local review for agricultural terminology and safety instructions. Do not depend on unreviewed machine translation for critical guidance.

### 9.3 Weak-network behavior

- Cache supported guides.
- Save task updates offline and sync safely.
- Show when weather or imagery is stale.
- Make camera outages visible.
- Label delayed detections with their original time.
- Offer low-data mode.
- Never turn a missing-data state into "Everything is safe."

## 11. Free-First Budget and Launch Boundaries

Free-first does not mean reliable 24/7 monitoring has no cost.

| Capability | Pilot approach | Possible later cost |
|---|---|---|
| Camera detection | Existing spare phone, on-device inference | Outdoor hardware, power, data |
| Weather | Cached eligible free/non-commercial access | Commercial API plan |
| Satellite | Open imagery, bounded processing | Processing quotas and compute |
| AI assessment | Available quota with explicit failure states | Inference usage |
| Notifications | Web Push | SMS/WhatsApp or other escalation |
| Evidence | Limited private storage and retention | Storage and transfer |
| Database | Existing project, efficient queries | Higher usage and capacity |

Open-Meteo's free hosted API is for non-commercial use. Monetization or affiliate revenue requires reviewing the applicable terms rather than assuming the free endpoint remains suitable.

Verify current provider availability, model support, licenses, quotas, and pricing before implementation or launch. No paid service should be activated without authorization.
